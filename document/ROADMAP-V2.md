## 🎯 Vision v2.0

Evolution from a **passive static scanner** into an **active Red Team Assistant** capable of proving, simulating, and confirming vulnerabilities directly at runtime.

> **Core Philosophy:**
> Static analysis finds *where* a vulnerability *might* exist.
> Dynamic analysis *proves* it is real — and demonstrates its impact.

## 🔌 Component 1: Frida Runtime Bridge

**Dependencies:** `frida`, `frida-tools`, Android Emulator / Physical Device (rooted)

### Description
Integration with **Frida**, the industry-standard dynamic instrumentation framework, to hook and trace Android applications directly at runtime.

### Sub-Features

#### 1.1 AI-Guided Hook Generator
- After a static finding is detected, DLH **automatically generates a Frida script** targeting the exact method/class flagged by the LLM.
- Input: `class_name`, `method_name`, `vulnerability_type` from the JSON report
- Output: A ready-to-run `.js` Frida script

```python
# Example flow:
finding = {
    "class": "com.example.DatabaseHelper",
    "method": "rawQuery",
    "vulnerability": "sql_injection"
}
# DLH generates:
# frida_hooks/sql_injection_DatabaseHelper_rawQuery.js
```

#### 1.2 IPC & Reflection Tracing
- Hook `Method.invoke()`, `DexClassLoader`, and Binder IPC calls
- Confirm dynamic dispatch vulnerabilities that cannot be verified through static analysis alone
- Detect class loading from unknown paths (dropper behavior)

#### 1.3 JNI Bridge Monitoring
- Trace calls crossing the Java/Native boundary:
  - `System.loadLibrary()`
  - `System.load()`
  - `RegisterNatives()`
- Detect hidden native code execution that is invisible to static analysis

#### 1.4 Crypto Hook
- Intercept cryptographic functions at runtime:
  - `Cipher.getInstance()` → extract the algorithm in use
  - `SecretKeySpec` → extract the key (if hardcoded)
  - `MessageDigest` → detect weak algorithms (MD5/SHA1)
- Output: Confirmation or rejection of `insecure_random_number_generation` findings

### Implementation Flow
```
1. Parse static finding
2. Identify target class + method
3. Generate Frida script template
4. Inject into the process via frida.attach()
5. Capture output / exception
6. Return verdict to the verifier
```

## 📱 Component 2: ADB Automation Engine

**Dependencies:** `adb` in PATH, Android Emulator (API 28+ recommended)

### Description
A structured **ADB command pipeline** to automatically launch, interact with, and monitor the target application.

### Sub-Features

#### 2.1 Auto-Launch & Intent Injection
- Automatically launch Activities, Services, and Broadcast Receivers identified by the manifest analyzer
- Send crafted Intents with fuzzing payloads based on exported component findings

```bash
# Example generated by DLH:
adb shell am start \
  -n com.example.app/.DeepLinkActivity \
  --es "url" "javascript:alert(document.cookie)" \
  --ez "debug" true
```

#### 2.2 Deep Link Fuzzer
- Generate and fire hundreds of `adb shell am start` deep link payloads
- Target exported Activities to find Open Redirect and Auth Bypass
- Payload library: path traversal, JavaScript injection, intent spoofing patterns

```
Payload categories:
├── javascript: injection     (WebView XSS)
├── file:///               (Local file access)
├── content://             (Content provider bypass)
├── intent://              (Intent spoofing)
└── custom://../../        (Path traversal in deep links)
```

#### 2.3 Logcat Correlation Engine
- Parse `adb logcat` output in real-time
- Feed relevant log lines to the LLM to confirm whether an exploit attempt succeeded or triggered an exception
- Keyword detection: `Exception`, `Caused by`, `SecurityException`, SQL error messages

```python
# Flow:
adb_logcat_stream → filter_relevant_lines() → LLM.analyze(
    prompt="Did this log indicate successful exploitation of SQL injection?",
    context=log_lines
) → verdict: "Confirmed" | "Not Triggered" | "Partial"
```

#### 2.4 Screenshot & State Capture
- Capture screen state before/after payload injection
- Document evidence: privilege escalation, sensitive data exposure, unauthorized screen display
- `adb shell screencap` → saved as an evidence artifact in the JSON report

## 🔍 Component 3: Runtime Vulnerability Verifier

**Dependencies:** Component 1 (Frida) + Component 2 (ADB)

### Description
A dedicated **verification pipeline** that takes a static finding and produces a confirmed or rejected verdict.

### Verification Pipeline

```
Static Finding (LLM)
        │
        ▼
Generate Runtime Probe
(Frida script / ADB command / Intent payload)
        │
        ▼
Execute via Frida/ADB
        │
        ├──────────────────────┐
        ▼                      ▼
   CONFIRMED ✅           REJECTED ❌
(Observable effect)    (No effect detected)
        │
        ▼
Attach Evidence:
- Logcat output
- Frida trace
- Screenshot
- HTTP response (if applicable)
        │
        ▼
Update Report:
status = "Verified" | confidence = "Confirmed"
```

### Verdict States

| Status | Meaning | Action |
|--------|---------|--------|
| `Verified` | Confirmed at runtime | Retain severity, attach evidence |
| `Unverified` | Static finding only | Downgrade confidence to `Medium` |
| `False Positive` | Runtime proves it is safe | Remove from final report |
| `Partial` | Effect detected but not conclusive | Flag for manual review |

### False Positive Eliminator
- Any finding that cannot be triggered at runtime is automatically downgraded to `status: "Unverified"`
- If Frida/ADB confirms no observable effect: `status: "False Positive"`
- The final report only shows `Verified` findings in the main summary

## 🌊 Component 4: Taint Analysis Engine

**Dependencies:** Existing Call Graph + optional FlowDroid JAR

### Description
A lightweight **Source-to-Sink** data flow tracker to verify whether user-controlled input reaches dangerous sinks without sanitization.

### Source Catalog

```python
SOURCES = {
    "intent_extras": [
        "getIntent().getStringExtra()",
        "getIntent().getIntExtra()",
        "getIntent().getBundleExtra()",
    ],
    "url_params": [
        "getQueryParameter()",
        "getPathSegments()",
        "getData().getHost()",
    ],
    "network": [
        "response.body().string()",
        "inputStream.read()",
        "BufferedReader.readLine()",
    ],
    "ui": [
        "EditText.getText()",
        "Spinner.getSelectedItem()",
    ]
}
```

### Sink Catalog

```python
SINKS = {
    "sql_injection":     ["rawQuery(", "execSQL(", "query("],
    "command_injection": ["Runtime.exec(", "ProcessBuilder("],
    "xss_webview":       ["loadUrl(", "loadData(", "evaluateJavascript("],
    "rce":               ["ObjectInputStream.readObject(", "DexClassLoader("],
    "file_write":        ["FileOutputStream(", "openFileOutput("],
    "path_traversal":    ["new File(", "getAbsolutePath("],
}
```

### AI-Assisted Path Reasoning
- When a full taint graph cannot be built statically, the LLM performs reasoning:
  - "Is there a plausible path from `getStringExtra()` to `rawQuery()` in this class?"
  - Based on the existing Call Graph context
- Result: `taint_path_probability: "High" | "Medium" | "Low"`

### FlowDroid Integration (Optional Plugin)

```yaml
# settings.yaml — optional
analysis:
  taint_engine: "lightweight"   # or "flowdroid"
  flowdroid_jar: "/opt/flowdroid/soot-infoflow-android.jar"
  android_jar: "/opt/android-sdk/platforms/android-33/android.jar"
```

## 🧩 Component 5: De-obfuscation Support

**Dependencies:** Proguard `mapping.txt` (optional) or LLM inference

### Description
Handling obfuscated APKs — the biggest practical challenge in real-world Android security assessments.

### Sub-Features

#### 5.1 Proguard Mapping Integration
- If a `mapping.txt` is provided alongside the APK, DLH automatically restores the original class and method names
- Flag syntax:
  ```bash
  python dlh.py scan target.apk --mapping mapping.txt
  ```
- Result: All output (reports, Frida scripts, PoC) uses original names instead of `a.b.c()`

#### 5.2 AI-Based Variable Renaming
- For APKs without a mapping file, the LLM analyzes obfuscated method bodies and proposes human-readable names based on behavior:
  ```
  a.b() → validateUserToken()    (reason: reads SharedPrefs + returns boolean)
  c.d() → encryptPayload()       (reason: Cipher.getInstance + Base64.encode)
  ```
- Naming suggestions are saved to `output/<apk>_deobfuscation_map.json`

#### 5.3 String Decryption Hints
- Detect common string encryption patterns:
  - XOR with a constant
  - Base64 chaining
  - AES/DES with a hardcoded key
- Flag for Frida-based runtime decryption:
  ```
  [HINT] String decryption detected at com.a.b.c.decrypt()
  → Suggested Frida hook: intercept return value at runtime
  ```

## 📊 Expected Impact of v2.0

| Metric | v1.x (Static Only) | v2.0 (Static + Dynamic) |
|--------|-------------------|------------------------|
| False Positive Rate | ~20–30% | **< 5%** (Runtime Verified) |

| Coverage | Visible source code patterns | Source + Runtime behavior + Taint paths |
| Evidence Quality | Code snippet + description | Code + Logcat + Screenshot + Frida trace |
| Obfuscation Resilience | Low (names unreadable) | High (Proguard mapping + AI renaming) |
